## 🚀 서비스 설명

> **"복잡한 경험 정리를 시각적인 마인드맵과 검증된 STAR 기법으로 완성하세요."**

사용자는 활동 타입 – 활동명 – 상세 경험으로 이어지는 구조를 통해 커리어 맵을 시각화하고, 핵심 역량 태그를 통해 체계적으로 관리할 수 있습니다.⛓️‍💥📑

### 🧠 나만의 경험을 모으는 개인 마인드맵
> **"단순한 기록을 넘어, 경험의 연결고리를 찾습니다."**

* **독립된 브레인스토밍**: 누구의 방해도 받지 않고 나만의 소중한 경험과 사례들을 자유롭게 펼쳐보세요.
* **직관적인 히스토리 정리**: 산발적으로 흩어져 있던 프로젝트와 에피소드들이 하나의 지도로 연결되는 과정을 경험할 수 있습니다.

![개인 마인드맵](https://github.com/user-attachments/assets/58d75fcf-3b29-4d68-85d5-a5502d124835)

<br/>

### 🤝 함께 정리하는 팀 마인드맵
> **"함께했던 프로젝트, 기억의 조각을 같이 맞춰보세요."**

* **실시간 공동 편집**: 링크 공유 한 번으로 팀원들을 초대하세요. 서로의 마우스 포인터와 편집 노드를 실시간으로 확인하며 생동감 있게 협업할 수 있습니다.
* **집단지성으로 완성하는 회고**: 팀 프로젝트의 성과와 에피소드를 동료들과 함께 정리하며, 놓치기 쉬운 세세한 디테일까지 완벽하게 기록하세요.

### ✍️ 성과를 증명하는 STAR 에피소드 보관함
> **"마인드맵에서 곧바로 이어지는 강력한 스토리텔링"**

미국 MBA와 국내 취업 시장에서 검증된 **STAR** 프레임워크를 적용하여, 마인드맵의 각 노드에 상세 에피소드를 바로 연결할 수 있습니다.

* **S (Situation) - 상황**: 당시 직면했던 구체적인 배경과 상황
* **T (Task) - 과제**: 해결해야 했던 문제나 달성해야 했던 목표
* **A (Action) - 행동**: 문제 해결을 위해 본인이 취한 구체적인 행동
* **R (Result) - 결과**: 행동의 결과로 나타난 성과 및 배운 점

## 🤝 협업 및 그라운드 룰

<details>
<summary>🌿 협업 전략 (브랜치 & 커밋 컨벤션)</summary>

### 브랜치 전략

우리 프로젝트는 **`dev` 브랜치를 메인 브랜치로** 사용합니다.

브랜치 흐름은 다음과 같습니다.

```
dev → (feat|fix|design|chore|refactor)/#이슈번호/작업내용
```


#### 📌 브랜치 운영 원칙

- **브랜치 단위**  
  하나의 **Issue = 하나의 작업 단위**입니다.  
  각 Issue는 작업 유형에 따라 아래와 같은 형식의 브랜치로 생성되며, 하나의 PR로 관리합니다.

  ```
  (feat|fix|design|chore|refactor)/#이슈번호/작업내용
  ```

- **브랜치 생성**  
  모든 작업은 Issue 생성 후, `dev` 브랜치에서 분기하여 진행합니다.

- **dev 브랜치 반영 방식**  
  작업 중 최신 변경 사항을 반영하기 위해,  
  rebase가 아닌 **merge commit 방식으로 `dev` 브랜치를 작업 브랜치에 병합**합니다.

- **Merge 규칙**  
  `dev` 브랜치로 병합 시 **최소 1명 이상의 Approve**가 필요합니다.

- **Merge 방식**  
  `dev` 브랜치로 병합할 때는 **Squash Merge**를 사용합니다.  
  이를 통해 하나의 Issue 작업이 하나의 커밋으로 정리되도록 유지합니다.


#### 🚀 배포 전략

- 배포는 `dev` 브랜치를 기준으로 진행합니다.
- 배포는 GitHub Actions **Release 워크플로우** 수동 실행으로 시작합니다.
- 수동 실행 시, 워크플로우가 **Semantic Versioning** 규칙에 따라 `v0.0.0` 형식의 **태그를 생성/푸시**합니다.
- 태그 생성을 트리거로 **배포 워크플로우가 자동 실행**됩니다.
- 배포 과정에서 **GitHub Release가 자동 생성**되며, 태그를 기준으로 배포/릴리즈 이력을 관리합니다.

<br/>

### 커밋 규칙
`type: 한글 메시지` 형식으로 작성합니다.

| type | 설명 |
| :--- | :--- |
| `feat` | 새로운 기능 추가 |
| `design` | CSS 및 디자인 수정 |
| `refactor` | 코드 리팩토링 |
| `fix` | 버그 수정 |
| `chore` | 설정 및 단순 기타 작업 |
| `docs` | 문서 수정 |
| `test` | 테스트 코드 추가 |

<summary>🎯 팀 그라운드 룰</summary>

### 🗣 말하기 규칙
* **용용체 사용**: 팀원 간 이쁘게 말하기를 실천합니다.
* **반론 시**: "2얏!" 외치고 손을 든 뒤, 반드시 **대안 또는 이유**를 제시하며 용용체로 말합니다.
* **공유**: 궁금한 것, 모르는 것, 지각/결석 상황은 즉시 공유합니다.
* **존중**: 주말 작업 및 야근을 당연하게 생각하지 않으며, 회의 시에는 존댓말을 사용합니다.

### 🕙 스크럼 및 회의
* **데일리 스크럼**: 매일 10:10(안부) / 10:30(본 회의) 진행.
* **회의 규칙**: 회의록 미리 읽어오기, 40분 회의 후 10분 휴식.
* **도망 규칙**: 자리 비울 시 "n분 숨겠습니다" 선언.

### 🍪 코드 책임제
* 본인도 설명하지 못하는 코드를 작성할 경우 **간식을 헌납**합니다.
* 모든 코드는 이유가 있어야 하며, 남에게 피해를 주지 않아야 합니다.

### ⛔ 위반 시 벌칙
* 엉덩이로 이름 쓰기 / 최후의 발언 / 정자체(줄임말 금지) 사용 / 음료 쏘기 중 선택.
